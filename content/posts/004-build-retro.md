上一版博客用现成的静态生成器。它什么都能做，代价是我每次想改一点东西，得先读懂它的插件系统。这次我把生成器整个换成了自己写的构建脚本，只依赖 `marked` 和 `gray-matter`。

## 换掉之后剩下的结构

```text
content/posts/*.md   文章（frontmatter + markdown）
src/styles, client   样式与交互源码
build/               生成脚本
docs/                产物，GitHub Pages 的发布目录
```

生成流程一共就四步：

1. 读 `content/`，解析 frontmatter；
2. markdown 转 HTML，顺手补标题 id、抽目录、算阅读时长；
3. 套模板字符串，写到 `docs/` 下的目录式路由；
4. 拷资源、写 RSS 和 sitemap。

真正决定页面长什么样的是 200 行模板，其余都是工具函数。

## 一个必须提前决定的人生问题：BASE_PATH

项目站点的地址是 `user.github.io/repo/`，用户站点是 `user.github.io/`。所有内部链接都必须带前缀，否则 CSS 和图片全 404。

我的做法是把前缀收敛到一个函数里，模板永远不写裸路径：

```js
// 只要经过 url()，斜杠就不会打架
config.base = normalizeBase(process.env.BASE_PATH || '/')
url('/archive/')  // '/repo/archive/' 或 '/archive/'
```

然后本地 `npm run dev` 用 `/`，CI 里从仓库名推出 `/repo/`。**绝对不要把带域名的绝对地址写进模板**，那样换仓库就全废了。

## 赔进去的东西

诚实记录：

| 现成生成器免费给你的 | 我自己写的成本                            |
| -------------------- | ----------------------------------------- |
| 增量构建             | 全量重建（当前规模 300ms，可接受）        |
| 图片优化             | 没有，只能手动压图（首页那张我压到 91KB） |
| 分页、相关 posts     | 没做，等真需要时再说                      |
| 多人协作约定         | 只能靠 README                             |

## 值得的地方

- 依赖从几十 MB 降到两个包，CI 时间掉到十几秒；
- 想加一个「月相」字段就加，不用查文档看它支不支持自定义字段；
- 出问题时栈只有一层，报错能直接看懂。

> 判断标准其实很简单：如果你打不开自己的构建产物去看看它为什么错了，那这个工具对你是负的。

## 结论

对个人博客这种规模（几百篇文章、单人写作、纯静态），自己写生成器是划算的。到了需要 i18n、评论系统、多作者权限的程度，请老老实实用现成的——那时候省下的时间，比自定义带来的快乐重要得多。
